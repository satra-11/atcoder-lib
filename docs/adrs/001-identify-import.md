# インポート文検知方式

### 1. 単純な文字列マッチ (Simple String Matching)

コードを行ごとに分割し、`startswith()` や `in` 演算子で判定する最も素朴な手法。

- **メリット:** 実装が極めて簡単。数行のコードでプロトタイプが完成する。
- **デメリット:** 圧倒的に脆い点。例えば `from  my_lib` のようにスペースが2つ入ったり、`import my_lib # 自作ライブラリ` のように行末にコメントが入るだけで破綻する。
- **総評:** スクリプトの動作確認レベルなら良いですが、長期的に運用するツールとしては信頼性が低い。

### 2. 正規表現 (Regular Expressions)

パターンマッチングを用いて、想定される揺らぎを吸収する手法。

- **メリット:** 空白の数や位置の違いに強く、目的のモジュール名だけをキャプチャグループで簡単に抽出できます。行単位で処理を行うため、実装が直感的。
- **デメリット:** 以下のようなケースで誤検知やパース漏れを起こすリスクがあり、Pythonの文法を「理解」しているため、限界がある。
  - 複数行インポート: `from my_lib import (\n  funcA,\n  funcB\n)`
  - 複数モジュールインポート: `import my_lib.math, my_lib.graph`
  - 文字列内のフェイク: `print("import my_lib")`（コードではなく文字列なのに反応してしまう）

- **総評:** 実装コストと実用性のバランスが最も取れた実利的なアプローチ。

### 3. 抽象構文木 (AST: Abstract Syntax Tree)

Python標準の `ast` モジュールを使い、ソースコードを文字列ではなく「意味のある木構造」としてパースする手法。

- **メリット:** 精度が100%。コメントや文字列内のフェイクは完全に無視され、いかに複雑な書き方をされていても、Pythonのインタプリタと同じ解釈で正確にインポートの依存関係（`Import` ノードや `ImportFrom` ノード）を抽出できる。
- **デメリット:** 実装のパラダイムが変わる。行単位の単純な置換ではなく、木構造をトラバース（巡回）して情報を集める必要がある。また、ASTから再び元のソースコード（文字列）を再構築する処理（`ast.unparse` など）が必要になり、コードのフォーマット（空行やコメント）が失われるなどの副作用に対処する手間が増える。
- **総評:** 本格的なLinterやFormatterを作る際の正攻法です。「Pythonの内部構造を学ぶ」という目的を最大化するのであれば、最も価値のあるアプローチ。
